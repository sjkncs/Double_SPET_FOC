## 一、产品使用场景

本系统为**宠物监控产品**的双轴运动控制单元：

| 轴 | 机构 | 运动特征 | 控制模式 | 指令方式 | 限幅 |
|---|---|---|---|---|---|
| **M1** | 无限转动圆盘 (水平旋转) | 连续旋转，无机械限位 | **位置模式 + 增量指令** | `g_M1_PosCmd += delta` | **2 RPM** (位置环速度输出限幅) |
| **M2** | 位置定位机构 (俯仰) | 有限行程 ±90° | **位置模式 + 绝对指令** | `g_M2_PosCmd = target` | **±90° = ±16384 counts** |

### M1 — 位置模式 + 增量指令

M1 是无限转动圆盘，视觉算法天然输出"往左转多少度"，用位置增量最匹配：

- **正常跟踪**: RK3576 发 `SET_MOTION(M1_delta=+100)` → STM32 累加 `g_M1_PosCmd += 100`
- **停止**: 不发增量 → 停在当前位置 (有保持力)
- **限速 2 RPM**: 通过位置环内环速度输出限幅 `g_M1_PosPID.out_limit = 2.0f`
- 无需归零——圆盘无机械限位，绝对位置数值无物理意义

**M1 溢出防护 (周期归零)**：

M1 持续累加 `g_M1_PosCmd`，在 2 RPM 下约 4.5 小时溢出 int32_t。宠物监控 24 小时运行，必须处理：

```c
// TIM3 ISR 控制周期边界执行 (原子，控制环无扰动)
if (abs(g_M1_PosCmd) > 1000000) {
    int32_t base = g_M1_PosFbk;
    g_M1_PosCmd -= base;
    g_M1_PosFbk -= base;    // 误差 (PosCmd - PosFbk) 不变
}
```

### M2 — 位置模式 + 绝对指令

M2 俯仰定位，RK3576 直接发目标角度：

- **跟踪**: RK3576 发 `SET_MOTION(M2_target=8192)` → M2 转到 +45°
- **限幅**: 固件 Clamp `g_M2_PosCmd` 到 ±16384 (±90°)，超出钳位
- **零点标定**: RK3576 上位机 [设定零点] 按钮 → 发 `TRIG_ZERO_CALIB(Motor=M2)`
- **无溢出风险**: ±16384 counts，int32_t 裕量 13 万倍

### 架构选型 — STM32 本地规划

RK3576 发低频路点 (≤200Hz)，STM32 侧负责斜坡/平滑。原因：
- 宠物跟踪场景 RK3576 视觉输出本就 ≤30fps，无需 1kHz 插补
- 消除 Linux 调度抖动对控制质量的影响
- Ramp 参数由 STM32 固件管理，RK3576 只需发目标

## 三、架构方案: while(1) 解析 + RX DMA + TX 双模

> **v1 修正**: 原方案将解析放在 IDLE ISR，评审后改为 while(1) 主循环解析。
> 理由：校准阻塞 while(1) 是应该修复的 bug，不是需要绕过的约束。

### 3.1 核心架构

```
 RK3576                    USART1                    STM32G474
 ──────                  ──────────                  ─────────
  │                                                      │
  │ ── 命令帧 (二进制) ──→  DMA RX Circular ──→ 环形缓冲区
  │                         IDLE ISR 只更新写指针        │
  │                                               while(1): Protocol_Poll()
  │                                               解析+CRC+执行全部命令
  │                                                      │
  │ ←── 状态帧 / VOFA ──  DMA TX ←── TIM4 填帧 ──┤
  │                                                      │
```

**分层职责**:

```
安全层:   看门狗超时 → 切零电流自由滑行              [TIM3 ISR 递增, while(1) 检查]
数据层:   USART1 RX DMA Circular → 填充环形缓冲区    [IDLE ISR 只更新写指针, 不解析]
主循环:   while(1) {
            Protocol_Poll();        // 解析环形缓冲区、CRC、执行全部命令
            Follow_M1M2_Poll();     // 主从随动
            M1_UpdateCtrlRef();     // 开环/步距角刷新
            M2_UpdateCtrlRef();
            M1_ClampParams();       // 参数安全钳位
            M2_ClampParams();
            FOC_UpdatePI_ByVbus();  // Vbus 自适应
            PollCalibTriggers();    // 校准状态机 (非阻塞)
            g_UpSeqNo++;            // 主循环存活证明
          }
控制层:   ADC ISR(17kHz) / TIM3 ISR(1kHz) / TIM4 ISR(1kHz)  [不变]
TX 双模:  TIM4 ISR 按模式选择填充协议状态帧或 VOFA 帧      [不变]
```

### 3.2 架构对比 (评审结论)

| 对比项 | IDLE ISR 解析 (v0) | while(1) 解析 (v1) |
|---|---|---|
| 代码复杂度 | 高 — ISR 内 CRC+帧解析+变量写入 | **低** — 主循环顺序执行 |
| 原子性风险 | 多处竞态 (ISR 写/TIM3 读/TIM4 读) | **几乎没有** — 单一上下文 |
| 命令队列 | 需要 ISR→while(1) 队列, 溢出风险 | **不需要** — 直接执行 |
| 延迟 (正常) | ~110µs | ~100µs (差异可忽略) |
| 校准期间 | 命令可达 (但不该接受运动命令) | 命令延迟 (状态机改造后消除) |
| 可调试性 | ISR 内断点影响实时性 | **主循环断点随便打** |

### 3.3 前置改动 (编码前必须完成)

| 改动 | 原因 | 工程量 |
|---|---|---|
| **加 RX DMA Circular Buffer** | 无 DMA 则 FIFO 溢出，与架构选择无关 | CubeMX 配置 + ~50 行 |
| **校准改非阻塞状态机** | 消除 while(1) 秒级阻塞 | ~2-3 天, HAL_Delay → 状态跳转 |

### 3.4 模式定义 (TX 双模, 与 v0 相同)

```c
enum CommMode {
    COMM_MODE_PROTOCOL = 0,   // 默认: TX 发协议状态帧
    COMM_MODE_VOFA,           // 调试: TX 发 VOFA JustFloat 帧
};
```

| 模式 | RX 行为 | TX 行为 | 触发方式 |
|---|---|---|---|
| PROTOCOL | while(1) 解析命令 | TIM4 填协议状态帧 | 上电默认 / 命令切回 |
| VOFA | while(1) 解析命令 (仍接受) | TIM4 走原 VOFA 引擎 | RK3576 发 SET_VOFA_MODE |

## 四、帧格式设计

### 4.1 通用帧结构

> **v1 变更**: Len 缩至 1B (Payload ≤ 255B 足够); CRC 覆盖范围扩展至含 Header。

```
┌──────┬──────┬──────┬──────────┬────────┐
│ 0xAA │ 0x55 │ Len  │ Payload  │ CRC16  │
│ (1B) │ (1B) │ (1B) │ (N Byte) │ (2B)   │
└──────┴──────┴──────┴──────────┴────────┘
```

| 字段 | 大小 | 说明 |
|---|---|---|
| Header | 2B | 固定 0xAA 0x55, 字节同步 |
| Len | 1B | Payload 字节数 (不含 Header/Len/CRC) |
| Payload | N B | `[CmdID(1B)] + [Data(N-1 B)]` |
| CRC16 | 2B | CRC-CCITT, **覆盖 Header + Len + Payload** |

- **最小帧**: 2+1+1+2 = **6 字节** (仅 CmdID, 无 Data)
- **最大帧**: Len ≤ 255

**v0→v1 变更说明**:
- **Len 2B→1B**: 所有预期帧 Payload < 50B, 1B 足够 (max 255), 每帧省 1 字节
- **CRC 覆盖 Header**: 降低数据流中 0xAA 0x55 伪帧头的误同步概率, 代码也更简单 (CRC 整帧除去 CRC 本身)

### 4.2 字节序

**所有多字节字段均为小端 (Little-Endian)**:
- `int16_t`: 低字节在前, 如 `0x1234` → 线序 `0x34 0x12`
- `int32_t`: 低字节在前, 如 `0x12345678` → 线序 `0x78 0x56 0x34 0x12`
- `uint16_t`, `uint32_t`: 同上
- CRC16: 低字节在前

这与 STM32 (ARM Cortex-M4, Little-Endian) 和 RK3576 (ARM Cortex-A72, Little-Endian) 的原生字节序一致, **Linux 端可直接 `memcpy` 到 packed struct, 无需字节交换**。

### 4.3 CRC-CCITT 规格

| 参数 | 值 |
|---|---|
| 算法名称 | CRC-CCITT (0xFFFF) |
| 多项式 | 0x1021 (x¹⁶ + x¹² + x⁵ + 1) |
| 初始值 | 0xFFFF |
| 输入反射 | 否 (MSB first) |
| 输出反射 | 否 |
| 最终异或 | 0x0000 (无) |
| 覆盖范围 | Header(2B) + Len(1B) + Payload(NB) |
| 帧内位置 | 紧跟 Payload, 低字节在前 |

**测试向量**: 对 ASCII 字符串 `"123456789"` (9 字节) 计算, 结果应为 `0x29B1`。

**Linux C 参考实现**:

```c
static const uint16_t crc_table[256] = {
    0x0000,0x1021,0x2042,0x3063,0x4084,0x50A5,0x60C6,0x70E7,
    0x8108,0x9129,0xA14A,0xB16B,0xC18C,0xD1AD,0xE1CE,0xF1EF,
    // ... 完整 256 项表见 STM32 固件 comm_protocol.c
};

uint16_t crc_ccitt(const uint8_t *data, size_t len) {
    uint16_t crc = 0xFFFF;
    for (size_t i = 0; i < len; i++)
        crc = (crc << 8) ^ crc_table[((crc >> 8) ^ data[i]) & 0xFF];
    return crc;
}
```

**Python 参考实现**:

```python
import crcmod
crc_func = crcmod.mkCrcFun(0x11021, initCrc=0xFFFF, xorOut=0x0000)
# 或手动: crc_func(b'\xAA\x55\x06\x10\x01\x00\x64\x00\x20')
```

- STM32 固件使用 256×2B 查表实现, 48 字节帧 CRC < 1µs
- CRC-16 对 < 256B 帧检错能力足够 (HD=4)
- 如后续需要 SIL2, 可升级为硬件 CRC-32 (STM32G4 内置), 帧尾改 4B

### 5.1b 命令 Payload 字节级定义

> 以下所有偏移均为 **Payload 内部偏移** (帧偏移 = Payload 偏移 + 3)。
> 多字节字段均为 **小端**。

**SET_MOTION (0x10)** — 主运动指令, ≤200Hz

|---|---|---|---|
| [0] | CmdID | u8 | = 0x11 |
| [1] | Motor | u8 | 0=M2, 1=M1 |
| [2:5] | Target | i32 | 绝对位置 (encoder counts), 小端 |

> **v3 变更**: 扩展为可选 payload, 向后兼容 4B/8B/12B 三种长度。

| 偏移 | 字段 | 类型 | 说明 |
|---|---|---|---|
| [0] | CmdID | u8 | = 0x12 |
| [1:2] | M1_Iq | i16 | M1 Iq 参考 (mA), 小端, 限幅 ±600 |
| [3:4] | M2_Iq | i16 | M2 Iq 参考 (mA), 小端, 限幅 ±600 |
| [5:6] | M1_Id | i16 | **可选** M1 Id 参考 (mA), 小端 |
| [7:8] | M2_Id | i16 | **可选** M2 Id 参考 (mA), 小端 |
| [9:10] | M1_AngleDelta | i16 | **可选** M1 电角度步进量 (Q15/ms) |
| [11:12] | M2_AngleDelta | i16 | **可选** M2 电角度步进量 (Q15/ms) |

- Payload 4B (CmdID+4B = 5B): 仅设 Iq
- Payload 8B (CmdID+8B = 9B): 设 Iq + Id
- Payload 12B (CmdID+12B = 13B): 设 Iq + Id + AngleDelta (开环转速)
- Id 写入 `g_Mx_Id_Hold_mA`, AngleDelta 写入 `g_Mx_AngleDelta_Target`
- 超时 30s 无新帧 → Iq + AngleDelta 均自动归零
- 通信看门狗触发 → Iq + AngleDelta 均自动归零

**AngleDelta 物理含义**: 每 1ms 控制周期的电角度增量 (Q15 格式)。示例: AngleDelta=100 ≈ 1.8 RPM (50 极对电机)

### 5.2 SET_MOTION 详解 (0x10)

> **v1 变更**: 从双轴速度改为 M1 位置增量 + M2 绝对位置; 加 SeqNo; M2 用 i16 (±16384 counts = ±90° 足够)。

```
Payload (6 字节):
  [0]    CmdID  = 0x10
  [1]    SeqNo  (u8, 0~255 循环)
  [2:3]  M1_delta   (int16_t, 小端, 单位: encoder counts)
  [4:5]  M2_target  (int16_t, 小端, 单位: encoder counts, ±16384 = ±90°)

完整帧: AA 55 06 10 xx xx xx xx CRC_LO CRC_HI = 11 字节
```

**传输耗时**: 11 × 10 / 1,152,000 = **95.5µs**

**执行路径**:
1. DMA 收完 → IDLE 中断更新写指针
2. while(1) 下一轮: Protocol_Poll() 校验 CRC
3. 有效帧: `g_M1_PosCmd += M1_delta`; `g_M2_PosCmd = M2_target`
4. 下一个 TIM3 tick (≤1ms) 使用新值

**M1_delta 范围**: int16_t ±32767 counts, @200Hz 最大速度 = 32767×200/65536×60 ≈ **6000 RPM** >> 2 RPM 限幅, 分辨率充裕。

**M2_target 范围**: int16_t ±32767, 需 ±16384 (±90°), 裕量 2 倍。固件 Clamp 到 ±16384。

### 5.3 QUERY_CAPS 详解 (0x01, v1 新增)

RK3576 上电后发一次，获取固件能力信息：

```
请求帧: AA 55 01 01 [CRC_LO CRC_HI]  — Payload 仅 CmdID(1B), 总帧 6B

响应 Payload (9 字节):
  偏移  字段          类型    说明
  [0]   CmdID         u8      = 0x81 (RSP_CAPS)
  [1:2] FwVersion     u16     固件版本 (主版本×0x100+次版本, 如 0x0100 = v1.0)
  [3]   ProtoVer      u8      协议版本号, 当前 = 1
  [4]   AxisCount     u8      轴数 = 2
  [5:8] Features      u32     特性 bitmask (小端)

响应完整帧: 2+1+9+2 = 14 字节
```

**Features bitmask 定义**:

| Bit | 名称 | 说明 |
|---|---|---|
| 0 | FEAT_VOFA | 支持 VOFA 调试输出 |
| 1 | FEAT_FOLLOW | 支持 M1→M2 主从随动 |
| 2 | FEAT_FLASH_PARAMS | 支持 Flash 参数存储 |
| 3 | FEAT_CURR_CALIB | 支持电流环 Rs/Ls 校准 |
| 4 | FEAT_KTH71_CALIB | 支持 KTH71 ANLC 校准 |
| 5 | FEAT_ZERO_CALIB | 支持电角度零点标定 |
| 6 | FEAT_STEP_CAPTURE | 支持阶跃响应录制 |

**RK3576 握手流程**:
1. 发 `QUERY_CAPS` (0x01)
2. 等待响应帧 (CmdID=0x81)
3. 验证 `ProtoVer >= 1`, 检查 `Features` 判断固件能力
4. 如 2 秒无响应 → 重试 3 次 → 报连接失败

### 5.4 Flash 擦除两步鉴权 (0x43 + 0x44, v1 新增)

> 评审建议随机 Token 鉴权。因宠物云台无安全攻击面，简化为固定 Magic + 条件校验。

```
步骤1: 发 FLASH_UNLOCK (0x43)
  → STM32 检查: 两电机均停止 + 无校准进行中
  → 满足: 置 g_FlashUnlocked = 1, 状态帧回报 SysFlags.FlashUnlocked=1
  → 不满足: 状态帧回报 LastCmdResult = ERR_MOTOR_ACTIVE

步骤2: 在 5 秒内发 FLASH_ERASE (0x44), Payload: Magic = 0xDEAD
  → STM32 检查: g_FlashUnlocked == 1 && Magic == 0xDEAD
  → 执行擦除, 清 g_FlashUnlocked
  → 超时或 Magic 错误: 清 g_FlashUnlocked, NACK
```

### 5.5 SET_IQ_REF 安全约束 (0x12, v1 增强)

- **仅 OpenLoop 模式下执行**, 其他模式返回 NACK (状态帧 LastCmdResult = ERR_WRONG_MODE)
- **超时保护**: 连续 30 秒无新 SET_IQ_REF 帧 → Iq **和 AngleDelta** 自动归零 (防堵转过热)
- **通信看门狗**: 超时 → Iq **和 AngleDelta** 自动归零 (零电流+停转)
- 已有 ClampParams 限幅: `IQ_LIMIT_MAX_MA = 600`

### 5.6 模式切换安全 (0x20, v1 增强)

- 模式切换在 **TIM3 ISR 控制周期边界执行** (原子操作)
- while(1) 收到命令后置标志 `g_Mx_PendingMode`, TIM3 ISR 下一 tick 生效
- 切换前强制 Iq 经斜坡归零 (4ms 渐降), 清 PI 积分
- 校准进行中拒绝 (NACK)

## 六、状态帧 (STM32 → RK3576)

### 6.1 周期状态帧

> **v2 变更**: 速度字段从 i16 dRPM (0.1 RPM) 升级为 **i32 milliRPM (0.001 RPM)**，电机块 14B→16B，Payload 39→43B。
>
> **理由**: 开环低速场景 (如 0.05 RPM) 需精确表示; i16 dRPM 最小步长 0.1 RPM 在 2 RPM 下仍有 5% 量化误差; milliRPM 彻底消除协议侧量化瓶颈。
>
> **注意**: 当前固件速度估算采用频率法 (编码器增量/TIM3 周期), 内部分辨率约 1 RPM。协议 milliRPM 忠实传递固件数据, 后续可升级为周期测量法以提升低速分辨率。

```
Payload (43 字节):
  [0]     CmdID          = 0x80 (STATUS)
  [1]     TxSeqNo        (u8, 状态帧自身序列号, TIM4 ISR 递增)
  [2]     LastRxSeqNo    (u8, 回报最后收到的命令 SeqNo)
  [3]     UpSeqNo        (u8, while(1) 递增 — 主循环存活证明)
  [4]     ProtoVer       (u8, 协议版本号 = 1)
  [5]     SysFlags       (u8, 见下方 bit 定义)
  [6]     LastCmdResult  (u8, 最后一条偶发命令的执行结果)
  [7:8]   Vbus_mV        (u16)
  [9:10]  CrcErrCount    (u16, 累计 CRC 校验失败次数)
  ---- M1 (16 字节) ----
  [11]    M1_CtrlMode    (u8)
  [12]    M1_Flags       (u8, bit0=VqSat, bit1=CalibActive)
  [13:16] M1_Speed_mRPM  (i32, 单位 0.001 RPM = milliRPM, 滤波后)
  [17:20] M1_PosFbk      (i32, encoder counts)
  [21:22] M1_Id_mA       (i16)
  [23:24] M1_Iq_mA       (i16)
  [25:26] M1_Id_Eff_mA   (i16, 三级自适应输出)
  ---- M2 (16 字节) ----
  [27:42] (与 M1 结构相同)

完整帧: 2 + 1 + 43 + 2 = 48 字节
```

**传输耗时**: 48 × 10 / 1,152,000 = **417µs**

**SysFlags 位定义**:

| Bit | 名称 | 说明 |
|---|---|---|
| 0 | FlashLoaded | Flash 参数已加载 |
| 1 | CalibInProgress | 任一电机校准中 |
| 2 | FlashUnlocked | Flash 擦除已解锁 (5s 超时) |
| 3 | CommWdgTripped | 通信看门狗已触发 |
| 4 | VofaMode | 当前处于 VOFA 模式 |
| 5~7 | Reserved | — |

**LastCmdResult 枚举**:

| 值 | 含义 |
|---|---|
| 0x00 | OK |
| 0x01 | ERR_UNKNOWN_CMD |
| 0x02 | ERR_WRONG_MODE |
| 0x03 | ERR_CALIB_ACTIVE |
| 0x04 | ERR_MOTOR_ACTIVE |
| 0x05 | ERR_FLASH_LOCKED |
| 0x06 | ERR_BAD_PARAM |

### 6.2 UpSeqNo — 从机主循环存活检测

> **v1 新增**, 来源: 评审报告 H1

**问题**: TIM4 ISR 还在跑 (帧到达正常), 但 while(1) 已挂死 → 帧结构完整, 数据冻结。

**三层检测**:

| 机制 | 谁递增 | 检测什么 | 响应 |
|---|---|---|---|
| 帧到达 (已有) | TIM4 ISR 发帧 | CPU 存活 / UART 通路 | RK3576 超时停止指令 |
| **UpSeqNo(u8)** | **while(1) 递增** | **主循环存活** | RK3576 检测 N 帧不变则报警 |
| IWDG (硬件) | while(1) 喂狗 | 主循环挂死兜底 | STM32 硬件复位 |

**关键**: UpSeqNo **必须由 while(1) 递增, 禁止在 TIM4 ISR 里递增**。

### 6.3 上报频率

| 频率 | TX 占用率 | 适用场景 |
|---|---|---|
| 100Hz | 417µs × 100 = 4.2% | 普通监控 (默认) |
| 200Hz | 8.3% | 较高观测率 |

**默认 100Hz**, 可由 SET_STATUS_RATE 动态调整, 最高 1kHz。

## 七、RX 接收架构

> **v1 重写**: DMA Circular + IDLE 写指针通知 + while(1) 解析。

### 7.1 DMA + IDLE 中断

```
USART1 RX DMA (v1 新增):
  - DMA 通道: DMA1_CH2 (DMAMUX 映射 USART1_RX)
  - 模式: Circular (环形缓冲)
  - 缓冲区: 128 字节
  - 触发: USART1 IDLE 中断 + DMA HTIF (半传输, 保底)

IDLE 中断 (优先级 6):
  - 工作: 读 DMA NDTR → 计算写指针位置 → 更新 g_RxDmaWrIdx
  - 不解析, 不校验, 不写业务变量
  - 耗时 < 1µs
```

### 7.2 while(1) 解析 — Protocol_Poll()

```c
void Protocol_Poll(void)
{
    while (rx_available()) {
        // 1. 在环形缓冲中查找 0xAA 0x55 帧头
        // 2. 读 Len, 检查数据是否攒够
        // 3. CRC-CCITT 校验 (覆盖 Header + Len + Payload)
        // 4. CRC 失败: g_CrcErrCount++, 跳过 1 字节继续找帧头
        // 5. CRC 通过: dispatch(cmd_id, payload, len)
        //    - 运动指令: 直接写全局变量
        //    - 校准触发: 置标志, PollCalibTriggers() 状态机推进
        //    - 模式切换: 置 g_Mx_PendingMode, TIM3 ISR 下一 tick 生效
        // 6. 更新读指针
    }
    g_CommWatchdogMs = 0;  // 本轮有有效帧则喂狗 (在 dispatch 内部)
}
```

### 7.3 IDLE 帧分裂容错

> **v1 新增**, 来源: 评审报告 M4

USB-UART 桥可能产生字节间隙, 一帧分裂为两次 IDLE 中断。处理方式:

- 解析器不依赖 IDLE 作为帧边界, 仅依赖字节流中的 0xAA 0x55 + Len + CRC
- IDLE 中断只更新写指针, while(1) 按字节流解析
- 超时保护: 帧头找到后 2ms 未凑满 → 丢弃, 重新找帧头

### 7.4 DMA 半传输保底

启用 DMA HTIF (Half Transfer Interrupt), 在缓冲区过半时也更新写指针。防止极端场景: IDLE 中断未触发 (如连续发送无间隙) 但数据已到达 DMA 缓冲区。

## 八、VOFA 共存机制

### 8.1 与现有 VOFA 引擎的关系

现有 `vofa_engine.c` 的 `Vofa_OnTIM4_1ms()` **完整保留**, 不做任何删改。上层新增调度层:

```c
void Comm_OnTIM4_1ms(void)   /* TIM4 ISR (1kHz, 优先级 10) */
{
    /* DMA 忙守卫: 上一帧尚未发完则跳过, 下一 tick 再试 */
    if (LL_DMA_IsEnabledChannel(DMA1, LL_DMA_CHANNEL_1)) return;

    if (g_CommMode == COMM_MODE_VOFA) {
        /* 确保 DMA 源地址指向 VOFA 帧缓冲区 (与协议帧缓冲区不同) */
        LL_DMA_SetMemoryAddress(DMA1, LL_DMA_CHANNEL_1, (uint32_t)&g_VofaFrame);
        Vofa_OnTIM4_1ms();
    } else {
        /* PROTOCOL 模式: 按分频计数器决定是否发送状态帧 */
        uint16_t len = build_status_frame();
        dma_tx_send(s_txBuf, len);
    }
}
```

### 8.2 模式切换流程

```
正常运行 (PROTOCOL 模式)
  ↓ RK3576 发 CMD 0x51 (SET_VOFA_MODE, VofaSrc=1, MotorSel=0)
  ↓ STM32: g_CommMode = COMM_MODE_VOFA; g_VofaSrc = ...; g_VofaMotorSel = ...
  ↓ TIM4 开始走 Vofa_OnTIM4_1ms() → USART1 TX 输出 JustFloat 流
  ...
  ↓ RK3576 发 CMD 0x52 (EXIT_VOFA)
  ↓ STM32: g_CommMode = COMM_MODE_PROTOCOL
  ↓ TIM4 恢复发送协议状态帧
```

### 8.3 VOFA 模式下命令处理

VOFA 模式下 while(1) 的 `Protocol_Poll()` **仍然运行**, 仍可接收并执行命令。TX 被 VOFA 占据, 无法发协议响应帧:

| 命令类型 | VOFA 模式下行为 |
|---|---|
| 运动指令 | 正常执行 (写变量), 无响应帧 |
| EXIT_VOFA | 执行后切回, 下一 TIM4 周期发状态帧 |
| QUERY_STATUS | 置标志, TIM4 下一周期临时插入一帧状态帧 |
| 校准触发 | 正常执行 |

### 8.4 对 vofa_engine.c 的影响

**零修改**。`vofa_engine.c` 保持独立模块, 只是上层调用者从 "TIM4 直接调" 变成 "Comm 调度层按模式选调"。

## 九、安全机制

### 9.1 通信看门狗

> **v1 变更**: 超时值从 50-100ms 缩短至 20ms (运动模式); 默认安全状态强制为方案A。

```
while(1) Protocol_Poll(): 收到有效帧 → g_CommWatchdogMs = 0
TIM3 1kHz: g_CommWatchdogMs++

if (g_CommWatchdogMs > g_CommTimeoutMs) {
    // 安全动作: 切开环, Iq=0, Id=0 → 电机自由滑行
}
```

| 场景 | g_CommTimeoutMs | 说明 |
|---|---|---|
| 运动模式 (Speed/Position/StepAngle) | **20ms** | 连续丢 20 帧 → 安全停止 |
| 空闲 / OpenLoop | **200ms** | 宽松, 允许偶发通信 |

**安全状态 — 强制方案A (零电流自由滑行)**:
- 切 OpenLoop, Iq_Ref=0, Id_Ref=0
- 电机失去保持力后自由停止
- 评审建议方案C (可配置) 暂缓——宠物云台失电自由滑行即可, 无需保持力

### 9.2 从机主循环存活检测

见 §6.2 UpSeqNo + IWDG。

### 9.3 指令安全

所有运动指令到达后，仍经过现有 ClampParams 限幅:
- M1: `out_limit = 2.0f` (RPM), 无限转
- M2: `PosCmd` Clamp ±16384 (±90°)
- `IQ_LIMIT_MAX_MA = 600`
- 校准进行中拒绝运动指令 (CalibInProgress 守卫)

### 9.4 CRC 校验

CRC 不匹配 → 整帧丢弃, 不执行, `g_CrcErrCount++`。通信质量通过状态帧回报可观测。

## 十、带宽与时序分析

### 10.1 典型场景: 200Hz 命令 + 100Hz 状态

```
时间轴 (5ms 周期, 200Hz 命令):
  0.000ms  RK3576 发送 11B 命令
  0.096ms  命令到达 DMA 缓冲区
  ~0.1ms   while(1) Protocol_Poll() 解析, 变量更新
  ...
  某 TIM4 tick: 48B 状态帧 DMA 发送 (每 10ms 一次 @100Hz)

UART 占用率:
  RX: 11B × 200 = 2.2KB/s → 1.9%
  TX: 48B × 100 = 4.8KB/s → 4.2%
  总占用: 6.0%, 余量 94%
```

### 10.2 极端场景: 1kHz 命令 + 1kHz 状态 (调试用)

```
RX: 11B × 1000 = 11KB/s → 9.5%
TX: 48B × 1000 = 48KB/s → 41.7%
总占用: 51.2%, 余量 49%
```

### 10.3 VOFA 模式

```
VOFA 帧: 44B × 1kHz = 44KB/s → 38.2% TX (VOFA 帧不变)
命令接收: 偶发 → 可忽略
总占用: ~38%
```

### 10.4 带宽总表

| 场景 | RX | TX | 总占用 | 余量 |
|---|---|---|---|---|
| **200Hz 命令 + 100Hz 状态 (典型)** | 1.9% | 4.2% | **6.0%** | **94%** |
| 200Hz 命令 + 200Hz 状态 | 1.9% | 8.3% | 10.2% | 90% |
| 1kHz 命令 + 1kHz 状态 (极端) | 9.5% | 41.7% | 51.2% | 49% |
| VOFA 调试 | ~0% | 38.2% | 38.2% | 62% |

**结论**: 1152000 baud 极为充裕。典型场景仅占 6% 带宽。v2 速度字段扩展仅增加 4B (44→48B)，影响可忽略。

## 十三、示例帧 (Hex Dump)

> 以下为上位机对接参考。CRC 值基于实际数据计算 (CRC-CCITT, init=0xFFFF)。
> 所有 hex 均为线序 (低字节在前)。

### 13.1 QUERY_CAPS (0x01)

```
TX → STM32:
  AA 55 01 01 [CRC_LO CRC_HI]
  |  |  |  |  └── CRC-CCITT(AA 55 01 01) = 待上位机计算
  |  |  |  └── CmdID = 0x01
  |  |  └── Len = 1
  |  └── Header[1]
  └── Header[0]
```

### 13.2 SET_MOTION (0x10) — M1 +100 counts, M2 到 8192 (45°)

```
TX → STM32:
  AA 55 06 10 07 64 00 00 20 [CRC_LO CRC_HI]
  |  |  |  |  |  |     |     └── M2_target=8192 (=0x2000, 小端: 00 20)
  |  |  |  |  |  └──── M1_delta=100 (=0x0064, 小端: 64 00)
  |  |  |  |  └── SeqNo=7
  |  |  |  └── CmdID=0x10
  |  |  └── Len=6
  |  └── Header
  └── Header
  帧总长: 11 字节
```

### 13.3 状态帧 (0x80) — 典型响应

```
RX ← STM32:  (48 字节)
  AA 55 2B 80 xx xx xx 01 xx xx yy yy zz zz
  |  |  |  |                          |  └── CrcErrCount(u16)
  |  |  |  |                          └── Vbus_mV(u16)
  |  |  |  └── CmdID=0x80 (RSP_STATUS)
  |  |  └── Len=43 (0x2B)
  |  └── Header
  └── Header
  后跟 M1 (16B) + M2 (16B) + CRC16 (2B)
```

### 13.4 FLASH_ERASE (0x44) — Magic = 0xDEAD

```
TX → STM32:
  AA 55 03 44 AD DE [CRC_LO CRC_HI]
  |  |  |  |  |  └── Magic 高字节 = 0xDE
  |  |  |  |  └── Magic 低字节 = 0xAD  (0xDEAD 小端)
  |  |  |  └── CmdID=0x44
  |  |  └── Len=3
  帧总长: 8 字节
```

## 十四、RK3576 端对接指南

### 14.1 串口配置 (Linux)

```c
// termios 配置要点
struct termios tty;
cfsetispeed(&tty, B1152000);  // 非标波特率, 需确认驱动支持
cfsetospeed(&tty, B1152000);
tty.c_cflag = CS8 | CREAD | CLOCAL;  // 8N1, 无硬件流控
tty.c_iflag = 0;                      // 禁用所有输入处理
tty.c_oflag = 0;                      // 禁用所有输出处理
tty.c_lflag = 0;                      // Raw 模式
tty.c_cc[VMIN] = 0;
tty.c_cc[VTIME] = 1;                  // 100ms 超时
```

### 14.2 接收状态帧流程

```
1. 从串口读取字节流
2. 搜索 0xAA 0x55 帧头
3. 读 Len (1字节), 等待 Len + 2 字节 (Payload + CRC)
4. 计算 CRC-CCITT(Header + Len + Payload)
5. 与帧尾 CRC16 (小端) 比较
6. 匹配 → 解析 Payload; 不匹配 → 跳过, 继续找帧头
```

### 14.3 从机存活检测 (UpSeqNo)

```
连续 N 帧 (建议 N=5) 状态帧的 UpSeqNo 不变 → while(1) 主循环挂死
→ RK3576 应停止发送运动指令, 报警
(TxSeqNo 仍递增说明 TIM4 ISR 活着, 但主循环已死)
```

### 14.4 通信看门狗注意事项

```
STM32 侧看门狗:
  - 默认超时: 200ms (空闲), 20ms (运动模式)
  - 超时动作: 切开环 + 零电流自由滑行
  - 任意有效帧 (CRC 通过) 即喂狗

→ RK3576 空闲时至少 5Hz 发 QUERY_STATUS (0x50) 保活
→ 运动模式至少 50Hz 发 SET_MOTION 保活 (200Hz 推荐)
```

## 十五、总结

**核心架构**: while(1) 主循环解析 + RX DMA Circular + TIM4 双模发送

**当前状态**: STM32 侧协议核心已实现 (`comm_protocol.h/c`), RK3576 可开始对接。

**关键参数速查**:

| 参数 | 值 |
|---|---|
| 波特率 | 1152000, 8N1 |
| 字节序 | 小端 (Little-Endian) |
| CRC | CRC-CCITT, poly=0x1021, init=0xFFFF |
| 帧头 | 0xAA 0x55 |
| 状态帧大小 | 48B (Payload 43B) |
| 状态帧默认频率 | 100Hz |
| 看门狗超时 | 200ms (空闲) / 20ms (运动) |
| 速度单位 | milliRPM (0.001 RPM, int32_t) |
| 位置单位 | encoder counts (65536 counts/圈) |

**关键优势**:
1. VOFA 零侵入保留 — `vofa_engine.c` 不改一行
2. 安全 — 看门狗 + 限幅 + CRC + Flash 鉴权
3. 带宽极充裕 — 典型场景仅占 6%
4. 协议版本 + QUERY_CAPS — 支持向前兼容
