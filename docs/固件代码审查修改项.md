## 一、必须修改 (1 处) — ✅ 已修改

### handle_flash_unlock() 缺少电机停止检查

**文件**: `Core/Src/comm_protocol.c`, `handle_flash_unlock()` 函数

**问题**: 协议文档 5.4 要求 "STM32 检查: 两电机均停止 + 无校准进行中"，但代码只检查了校准状态，没检查电机是否在运行。

**风险**: 如果电机正在闭环运行 (如速度模式 1000RPM)，UNLOCK 通过后 5 秒内 ERASE 到来，`FlashParams_EraseAndReset()` 执行 `LL_HRTIM_DisableOutput` 关 PWM，旋转中的电机突然失去驱动力——对负载机械是不受控的突发失力。

**固件侧裁定**: ✅ **确实是遗漏**。`CMD_ERR_MOTOR_ACTIVE = 0x04` 错误码在 `comm_protocol.h` 第 109 行已预定义，说明设计时就计划做此检查但实现时遗漏。

**已执行的修改**:

```c
static void handle_flash_unlock(void)
{
    /* 校准进行中禁止 Flash 操作 */
    if (g_CurrLoopCalibInProgress_M1 || g_CurrLoopCalibInProgress_M2) {
        s_lastCmdResult = CMD_ERR_CALIB_ACTIVE;
        return;
    }
    /* FlashParams_EraseAndReset 会关 HRTIM PWM, 闭环运行中执行会导致失力 */
    if (g_M1_CtrlMode != MODE_OPEN_LOOP || g_M2_CtrlMode != MODE_OPEN_LOOP) {
        s_lastCmdResult = CMD_ERR_MOTOR_ACTIVE;
        return;
    }
    s_flashUnlocked   = 1;
    s_flashUnlockTick = HAL_GetTick();
    s_lastCmdResult   = CMD_OK;
}
```

## 二、需要加注释 (2 处)

### 2.1 handle_set_motion 成功路径故意不写 CMD_OK — ✅ 已修改

**文件**: `Core/Src/comm_protocol.c`, `handle_set_motion()` 函数末尾

**现状**: 成功时不写 `s_lastCmdResult = CMD_OK`，而其他命令 (如 `handle_set_position`) 都写了。看起来像漏了。

**辩论结论**: 这是正确的设计——SET_MOTION 是 200Hz 高频命令，如果每帧都写 CMD_OK，会覆盖掉偶发命令 (如 SET_CTRL_MODE 返回的 ERR_CALIB_ACTIVE) 的诊断结果，上位机来不及读到错误。

**但代码没有注释说明意图**，下次维护者可能当成 bug "修复"掉，反而破坏设计。

**固件侧裁定**: ✅ **采纳**。分析精准，确实需要注释防误改。

**已执行的修改**: 在函数末尾加注释:

```c
    g_M2_PosCmd = (int32_t)m2t;

    /* 故意不写 s_lastCmdResult = CMD_OK:
     * SET_MOTION 是高频运动指令 (≤200Hz), 不应覆盖偶发管理命令的诊断结果,
     * 否则上位机无法通过 LastCmdResult 观察到配置/校准命令的错误 */
}
```

### 2.2 VOFA 模式下 DMA 地址恢复 — ⏭️ 无需修改 (已有注释)

**文件**: `Core/Src/comm_protocol.c`, `Comm_OnTIM4_1ms()` 函数中 VOFA 路径

**审查者说**: 第 645 行 `LL_DMA_SetMemoryAddress(...)` 看起来像多余操作，需加注释。

**固件侧裁定**: ⏭️ **该行已有注释，评审者可能看的是旧版代码快照。** 当前代码第 678 行:

```c
/* 正常 VOFA 路径: 确保 DMA 源地址指向 VofaFrame (可能被协议帧改过) */
LL_DMA_SetMemoryAddress(DMA1, LL_DMA_CHANNEL_1, (uint32_t)&g_VofaFrame);
```

已充分说明意图，无需重复修改。
